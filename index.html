01

TEAM CAPSTONE · UNITY / C# / VR / HARDWARE

In development開発中

DriVR

What happens when the code says an input is correct, but the steering wheel in your hands says otherwise?

コード上では正しい入力なのに、手元のステアリングがそう感じさせないとしたら？

DriVR is my university capstone: a small team is extending an existing VR driving application. My part sits where software meets physical hardware—Logitech G920/G29 support, manual shifter input, Quest 3 controller mapping, VR-only controls and steering response.

DriVRは、既存のVR運転アプリを小規模チームで拡張する大学の卒業制作です。私はソフトウェアと実機が接する部分を担当し、Logitech G920/G29、物理シフター、Quest 3の入力マッピング、VRのみで行う操作、ステアリング応答を開発しています。

DEBUG TRACE / STEERING

The centre felt dead.中央付近で反応が鈍い。

Instead of tuning the car by feel, I traced the input path and tested the hardware against the application.

感覚だけで車両を調整するのではなく、入力経路を追い、実機とアプリの挙動を照合しました。

  1. SYMPTOM

    Small wheel movements near centre produced little response.

    中央付近の小さな操作に車両がほとんど反応しない。

  2. TRACE

    Input handling revealed deadzone behaviour between the device and game.

    デバイスからゲームまでの入力処理を追い、デッドゾーンの影響を特定。

  3. TEST

    Changes were checked with the physical Logitech wheel—not only in the editor.

    エディター上だけでなく、Logitechの実機で変更を検証。

  4. ADJUST

    The implementation was updated until centre input behaved responsively.

    中央付近でも自然に反応するよう実装を調整。

Another assumption testedもう一つ、実機で覆した想定

An early mapping treated sixth gear as reverse. Physical testing showed that the G920 uses a push-down mechanism before moving into reverse. I changed the mapping so sixth remained available and reverse matched the hardware.

初期の入力設定では6速位置をリバースとして扱っていました。しかし実機では、シフターを押し込んでからリバース位置へ動かします。そこで6速を保持しつつ、実際の機構に合うリバース入力へ変更しました。

02

PERSONAL PROJECT · JAVASCRIPT / VITE / AI APIS

In development開発中

VN Playground

I wanted to know what changes when generative models become parts of an application—not just tools behind a chat box.

生成モデルを単なるチャットツールではなく、アプリの構成要素にしたら何が変わるのかを確かめたい。

VN Playground is a browser-based visual roleplay project. It turns generated stories into navigable visual-novel pages, coordinating narrative output, dialogue parsing, image prompts, image generation and saved application state.

VN Playgroundは、ブラウザで動くビジュアル・ロールプレイの個人プロジェクトです。生成された物語をページ単位で移動できるビジュアルノベルとして構成し、文章生成、会話解析、画像プロンプト、画像生成、状態保存を一つの流れにまとめています。

What exists now現在の実装

Scenario and character cards, dialogue and narration parsing, multiple saved chats, turn navigation, regeneration controls, browser-local image storage and provider-specific settings.

シナリオ・キャラクターカード、会話・ナレーション解析、複数チャットの保存、ターン移動、再生成、ブラウザ内の画像保存、プロバイダー別の設定を実装しています。

What I am learning現在の学び

Different providers do not behave like interchangeable boxes. Prompt structure, model limits, asynchronous jobs, storage and failure states all become application-design problems.

プロバイダーは単純に交換できる箱ではありません。プロンプト構造、モデルの制約、非同期処理、保存、失敗時の状態まで、すべてがアプリ設計の課題になります。

How it is evolving開発の進め方

The app remains intentionally vanilla JavaScript while it is refactored into clearer domain, storage and provider modules, with Vitest characterisation tests protecting behaviour.

現在はVanilla JavaScriptを維持しながら、ドメイン・保存・プロバイダーごとに責務を分離するリファクタリングを進め、Vitestの特性テストで既存挙動を守っています。

03Personal tool個人ツール

PYTHON / ANKI / KANJIVG / KANJIDIC2

auto_kanji_info

The problem began in my own study routine: too much repeated work collecting the same kanji information for sentence-mining cards.

きっかけは、自分の学習で感じた不便でした。センテンスマイニング用カードに同じ漢字情報を何度も手作業で集めていました。

I built an Anki add-on that hooks into note creation, finds each unique CJK character, and fills readings, meanings, stroke count, frequency, radicals and components from a local dataset. A bulk action handles older notes, while existing fields are preserved by default.

そこで、ノート追加時にCJK文字を抽出し、ローカルデータから読み・意味・画数・頻度・部首・構成要素を自動入力するAnkiアドオンを開発しました。既存ノートは一括処理でき、初期設定では入力済みの内容を上書きしません。

The useful lesson得られたこと

Small personal friction can be a good software brief—because the user, constraints and definition of “better” are all real.

日々の小さな不便は、良い開発テーマになります。利用者も制約も「何が改善か」も、すべて実在するからです。

04Supervised internship work指導下のインターン演習

MICROSOFT DEFENDER / ADVANCED HUNTING / OSINT

A signal is not a conclusionアラートは結論ではない

During my Spark internship, investigation exercises repeatedly came back to one question: what evidence would distinguish suspicious behaviour from an unusual but legitimate event?

Sparkのインターンで調査演習に取り組む中、繰り返し向き合ったのは「不審な挙動と、珍しいが正当な操作を、どの証拠で区別するか」という問いでした。

I reviewed process trees, command-line context, device timelines, sign-in history, MFA status, URLs, domains and IP reputation. One anomalous location became a false positive only after the wider sign-in pattern and travel timing supported that conclusion.

プロセスツリー、コマンドライン、端末タイムライン、サインイン履歴、MFA状態、URL・ドメイン・IPレピュテーションを確認しました。異常な地域からのログインも、過去のパターンと移動時間を照合して初めて、誤検知という結論を裏付けられました。

The useful lesson得られたこと

Investigation is less about reacting to an alert than building a conclusion another person can follow.

調査はアラートに反応するだけでなく、他の人が追える根拠を積み重ねて結論を作ることだと学びました。
